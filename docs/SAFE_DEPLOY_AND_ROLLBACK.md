# 安全部署与回滚手册（只读文档，禁止在生产执行）

这份手册给以后真正核对过版本的人看。按 2026-11-10 的仓库和审计，**现在就不能进入部署**。`scripts/deploy_safely.sh` 会在发现没有 `backend/app/routers/nce.py` 时直接退出。不要为了绕过它去设确认变量。

## 两条硬门槛

两条都过了，才允许讨论重启容器。过了一条不算。

### 1. 版本核对

必须同时满足：

1. 运行中的前端镜像、后端镜像能对应到一份含 `/api/nce` 和四册新概念的源码，而不只是 GitHub `4381616`。
2. 那份源码的提交号写进镜像标签或发布记录。服务器目录目前没有 `.git`，不能用「目录里看起来像」代替提交号。
3. 线上 OpenAPI 路径、新概念四册、词频和六级卷在候选版本里都还在。本仓库 `next build` 没有新概念页面，不合格。
4. 候选版本不会在启动时对线上库执行未评审的 `ALTER`。当前 `init_db()` 会给已有表补列；在版本未核对前，不要用这份代码去打开线上库。

核对不过就停止。不要 `git clone` 后覆盖 `/home/ubuntu/sixsense`，不要 `rsync --delete`，不要 `docker compose build` 这棵树。

### 2. 备份与恢复演练

线上库约 25.6MB，路径 `/home/ubuntu/sixsense/data/sixsense.db`，挂在后端容器的 `/app/data`。审计时旁边没有 `.db-wal` / `.db-shm`，当时也没有 sqlite3 命令，所以 **WAL 模式并未证实**。应用代码每次连接都会执行 `PRAGMA journal_mode=WAL`。安静时 WAL 文件可以不在，一有写入就会出现。只复制 `.db` 会漏掉尚未合并的 WAL。

正确快照是 SQLite 备份 API（`Connection.backup`），它会把已提交的 WAL 帧收进一个完整文件。`scripts/backup_db.py` 用的就是这个 API，再 gzip。服务器上那些 `sixsense.db.bak_*` 是临时文件，脚本内容审计时没有核对，不能当作这轮的合格备份。

演练只许在副本上做：

```bash
python3 scripts/sqlite_backup_restore_drill.py
```

脚本拒绝这些路径和文件：`/home/ubuntu/sixsense`、`43.142.98.29`、`mystone.top`、仓库里的 `data/sixsense.db`、`.env`、音频。2026-11-10 在临时目录的结果是：写入方还开着且 WAL 文件非空时完成快照，恢复出 2 行合成数据，`PRAGMA integrity_check` 为 `ok`。这不是线上库的恢复证明。

上线前还要在**副本**上做一次同样的演练，副本来自备份 API，不来自把生产库提交进 Git。演练不过就停止。

备份范围只包括 SQLite 快照。不要把用户表导出到仓库、工单或测试。不要备份或覆盖时带上 `.env`、`.jwt_secret`、`data/audio`、新概念媒体目录。审计只确认新概念数据约 7.4MB、四册都在，没有给出可以删除的路径；未知目录一律保留。

仓库里的 4.3MB `data/sixsense.db` 不是线上库。用它覆盖线上文件会丢掉线上内容和用户数据。

## 健康检查

候选版本如果有一天被允许启动，只检查本机回环，不把审计机的外网 TLS 当健康标准：

- `GET http://127.0.0.1:8000/api/health` 返回 200，正文仍是服务存活信息。
- 新概念接口仍返回四册，而不是 404。
- 六级卷列表的年份数量不比切换前少。
- 数据库文件字节数没有突然掉到仓库那份 4.3MB 的量级。
- 容器 `restart_count` 不增加。
- 抽查只看状态码和册数，不把用户记录打出来。

外网 443 的 TLS EOF、HTTP 被 DNSPod 拦到备案页，都不要当成应用没起来，也不要当成备案完成或国内可用。

## 停止条件

出现任一条，立刻停止，不要继续重启、不要改 Nginx、不要改 DNS、不要删卷：

- 版本门槛或备份演练有一条没过。
- 源码树里没有新概念实现，却准备重建 `sixsense-frontend` / `sixsense-backend`。
- 健康检查不是 200，或新概念接口消失。
- 数据库变小、打不开，或 `integrity_check` 不是 `ok`。
- 磁盘剩余空间不够再放一份完整快照（线上库本身只有几十 MB，但不要顺手复制整个数据目录或音频）。
- 需要查看或拷走用户表才能继续。

`start.sh` 如果发现自己跑在 `/home/ubuntu/sixsense` 或主机名 `VM-0-12-ubuntu` 上，也会直接退出。

## 回滚

回滚对象是上一份已经在跑的镜像和备份 API 产生的库文件，不是 GitHub `main`。

1. 不要删正在使用的 `sixsense.db`、它的 `-wal`/`-shm`、新概念目录和音频。
2. 停止写入后，用备份 API 把合格快照恢复到一个新文件，再跑 `integrity_check`。
3. 只有检查通过，才在进程已停止写入时用新文件替换。替换前把当前文件改名留下，确认健康检查和新概念册数都在，再考虑删掉改名文件。
4. 容器回到切换前的镜像 ID。2026-11-10 审计见到的是前端 `sha256:106de2a816a125499671012b3dae2411b21b119b32116c3f63efcc28079e191a`，后端 `sha256:d1ea9ac25f3abfb17cea3c235a3d9a6f62bbcfc2e681a75446a6ad7ea4e06771`。这两份镜像不是本分支构建的，本分支也没有验证它们的层内容。
5. 健康检查失败就停在改名后的旧文件上，把进程指回去。不要在失败后再跑一次迁移或清空数据。

## 明确不在本手册里执行的动作

不合并，不部署，不改 DNS，不改 Nginx，不重启线上容器，不把线上库传到这台开发机或仓库，不改表结构，不重建数据卷。端口收回到本机地址是审计建议，等版本核对之后单独做，不放进这次差异里。
